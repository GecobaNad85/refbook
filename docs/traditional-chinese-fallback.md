# 划词查询繁体字处理 —— 实现思路分析

> 需求原文：分析当划词查询的内容包含繁体字时，先根据繁体字内容进行查询（包括无结果分词查询），需再加上整体繁体字转简体字再查询的思路。
>
> 本文档仅做**实现思路分析**，不涉及代码改动。待思路确认后再进行修改。

---

## 1. 现状梳理（基于现有代码）

### 1.1 划词查询总入口

`content.js` 中 `mouseup` 事件处理器（约 line 638-665）：
```
选中文本 selectedText
  → lastKeyword = selectedText
  → queryWithSegmentation(selectedText, x, y, gen)   // 唯一查询总入口
```

### 1.2 查询主流程 `queryWithSegmentation(keyword, x, y, gen)`（约 line 1113）

```
步骤1：整词查询  searchRefbook(keyword)
步骤2：有结果 → renderResults(data, x, y, keyword) + autoFetchFullText（不分词）
步骤3：无结果 → showLoading('整词未命中，正在分词检索...')
         → segmentKeywordSmart(keyword)  // SegmentIt 智能分词，失败回退滑动窗口
步骤4：无段可分词 → 显示空结果
步骤5：并行查询所有候选词段  searchRefbook(seg.text)
步骤6-9：筛选有结果词段 → 贪心选不重叠 → 构建多标签 tabs → renderTabbedResults()
```

### 1.3 另一查询入口：图标搜索框 `performSearch`（约 line 1488-1520）
- 读取输入框 `keyword`
- 调用 `searchRefbook(keyword)`，有结果直接渲染，无结果**不**分词（该入口无分段逻辑）

### 1.4 真正发请求的地方
- `background.js searchRefbook(keyword)`：POST `t.cnki.net/rbook-api/v1/criteria/query`，`uv: keyword` 精确匹配词目（`uf:"ET"`）
- 有 `resultCache`（key = trim 后关键词，5 分钟 TTL）
- **注意**：简繁转换后访问缓存时，简体作为新 key，会与繁体 key 分别命中

### 1.5 现状结论
- 当前代码**完全没有**繁体/简体的检测与转换逻辑（前文已 grep 确认：无 Traditional/Simplified/OpenCC 相关代码）。
- 选中繁体直接以繁体原文去查；CNKI 词目标的是简体词目库，繁体整词大概率查不到 → 走分词 → 分词也是繁体 → 仍可能查不到。

## 2. 需求拆解与目标

需求要实现的查询策略（当**选中内容含繁体字**时）：

```
选中内容（可能含繁体）
    │
    ├─ 分支 A：按【繁体原文】查询
    │    ├─ 整词查询（重现有逻辑）
    │    └─ 无结果 → 繁体分词查询（重现有逻辑）
    │
    └─ 分支 B：整体【繁体→简体】转换后，再查一遍
         ├─ 简体整词查询
         └─ 无结果 → 简体分词查询
```

最终期望：**命中率更高**。繁体原文查不到时，靠简体版本补上；反之亦然。

## 3. 关键设计决策点

### 3.1 决策点1：简体转换放在哪个层？

| 方案 | 位置 | 优点 | 缺点 |
|------|------|------|------|
| **A. 纯前端（content.js）** | 选中文本后、`queryWithSegmentation` 前用 JS 库转换 | 无需改 background；无网络依赖；即时 | content script 受 CSP 限制，需类似 SegmentIt 用 sandbox iframe 加载 OpenCC |
| **B. background.js** | 在 `searchRefbook` 内部，收到繁体时先转简体再查 | 查询逻辑集中；缓存可统一 | 改了 API 语义，会影响"精确匹配繁体词目本身"的场景 |
| **C. 后端/代理** | 服务端转换 | 无前端负担 | 本项目是无后端的纯扩展，不适用 |

**建议：方案 A**，与现有 SegmentIt sandbox 模式一致，最小侵入。

### 3.2 决策点2：简繁转换库选型

| 库 | 特点 | CSP 适配 |
|----|------|----------|
| **OpenCC**（`opencc-js`） | 权威、词级转换、简繁 vs 繁简词典齐全 | ES module，可放入 sandbox iframe 从 CDN 加载 |
| **HanziConv** 等轻量库 | 体积小，逐字转，词级优化弱 | 简单，但多音字/词级"皇后→皇后"等场景不准 |
| 自建字符映射表 | 可控但巨大且维护难 | —— |

**建议：OpenCC（opencc-js）**，词级精度高。sandbox iframe 已存在（`sandbox.html` 用于加载 SegmentIt），可复用同一套 postMessage 通信通道。

### 3.3 决策点3：如何判定"含繁体字"？

- 不必每次 100% 转换。先用轻量检测：统计文本中是否存在 `\u4e00-\u9fff` 且当前字形属于繁体编码区/特点字。
- 严谨做法：OpenCC 提供反向判断，或维护小集合判断（如"體、發、灣、臺、廣、龍、魚、門、車、東"等高频繁体）。
- 简化做法：**只要字符串与"繁→简"转换结果不同，就认定含繁体**，从而触发分支 B。

### 3.4 决策点4：两条分支如何组织 / 展示？

这是核心的 UI 设计问题，有三个候选：

**方案①：串行兜底（最简）**
```
繁体整词 → 有结果? 展示
        → 无? 繁体分词 → 有? 展示
                       → 无? 简体整词 → 有? 展示
                                      → 无? 简体分词 → 有? 展示
                                                    → 无? 空
```
- 优点：改动小，沿用现有 `queryWithSegmentation` 逻辑，只是把"无结果"的兜底链再延伸一层。
- 缺点：串行多次请求，慢；若繁体整词/分词有部分结果，不会自动补充简体结果。

**方案②：并行 + 合并标签（推荐）**
```
并行发起：
  繁体整词、繁体各分词、简体整词、简体各分词
  → 汇总 → 去重 → 按"整词优先、简体优先、长度优先"排序
  → 渲染多标签（提示哪些是简体转换结果）
```
- 优点：一次完成、体验快；结果丰富。
- 缺点：改造 `queryWithSegmentation` 较大，需合并去重、管理标签分组。

**方案③：分阶段 + 用户可选**
- 先按繁体查（体验与现在一致）；空/不佳时在弹窗底部加"以简体再查"按钮。
- 优点：语义最清晰，不打扰。
- 缺点：多一次用户交互；自动性弱于需求描述（需求倾向于自动补查）。

**综合结论**：需求明确说"**需再加上**整体繁体字转简体字再查询"，倾向**自动追加**。推荐**方案②（并行+合并）**或**方案①（串行兜底）**。建议先上方案①（改动小、风险低），视效果再演进到方案②。

## 4. 推荐实施路径（待确认后落地）

### 阶段一：检测 + 转换基础能力
1. 在 `sandbox.html` 中，与 SegmentIt 并列加载 `opencc-js`（通过 postMessage 通信）。
2. 新增 `detectTraditional(text)` 与 `toSimplified(text)` 两个辅助函数（content.js）。
3. 复用/扩展 sandbox postMessage 协议：新增 `cnki-t2s` 请求类型。

### 阶段二：接入查询主流程
4. 修改 `queryWithSegmentation`：开头检测 `detectTraditional(keyword)`。
   - 命中 → 记录 `simplified = toSimplified(keyword)`，并进入分支 A → B。
   - 未命中 → 保持现有逻辑（零影响）。
5. 分支 A：现有繁体整词+分词逻辑不动。
6. 分支 B：对 `simplified` 执行同样的整词+分词查询。

### 阶段三：结果组织与展示
7. 串行兜底（方案①）：把分支 B 作为"完全无结果"之后的追加尝试。
8. 或并行+合并（方案②）：汇总去重、多标签、标注"简体"来源。

### 阶段四：缓存与边界
9. background `resultCache` 按简体 key 自然生效（简体与原繁体是不同 key）。
10. 边界处理：
    - 简体==繁体（无变化）→ 不重复转换/查询。
    - 含英文/数字混合 → OpenCC 只转中文部分。
    - 空白/超长文本 → 沿用现有 trim 与长度保护。
    - 分词在简体与繁体下段可能不同（如"發展"→"发展"），需各自处理。

## 5. 风险与注意点

| 风险 | 说明 | 对策 |
|------|------|------|
| **CSP 限制** | content script 不能直接 eval；需 sandbox iframe | 复用现有 `sandbox.html` 通道 |
| **转换精度** | 繁体→简体一般很可靠；个别多音/异体可能歧义 | 用 OpenCC 词库而非逐字映射 |
| **请求数增加** | 分支 B 增加若干网络请求 | 并行为主；控制 size；利用缓存 |
| **结果重复** | 繁体与简体可能命中同一词条 | 按 fn（条目ID）去重合并 |
| **缓存语义** | 不同 key，需分别缓存 | 保持现状即可 |
| **性能/首查延迟** | 首次加载 opencc 词典有下载开销 | 懒加载（与 SegmentIt 预热策略一致） |

## 7. 结论

- 现有架构（`queryWithSegmentation` 单一入口 + sandbox 通道 + 多标签渲染）**完全支持**新增繁体→简体补查。
- 最稳妥落地 = **复用 sandbox 加载 opencc-js + 在 `queryWithSegmentation` 内串行追加简体兜底**。
- 是否升级到并行合并，取决于对"结果丰富度 vs 改动风险"的取舍。
